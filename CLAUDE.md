# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Personal, local-only tool that indexes TV episodes (Avatar: The Last Airbender) into searchable scenes, so footage can be found by meaning for video editing / scriptwriting. FastAPI + SQLite backend in `backend/`, React + Vite frontend in `frontend/`. Windows machine with a CUDA GPU (PyTorch must be the CUDA build - `torch==2.14.0+cu130` from the cu130 index - or every embedding silently runs on the CPU, ~100x slower); `ffmpeg` and (for the default caption provider) the `claude` CLI must be on PATH.

`TODO.md` holds the backlog and known data-quality issues; `ideas.md` (Russian) describes the larger planned workflow this feeds into (voice-over, automatic video assembly). `README.md` is partly outdated - prefer the commands below.

## Data

Everything the app keeps lives outside the repo, in one folder: `ROOT_DIR` in `backend/.env` (`app/config.py`; without it, `backend/data`) - here `D:/lorecut`. Inside it:

```
index/      (<data> below, config.DATA_DIR) index.db, keyframes/, audio/, comics/, settings.json, universes.json
  logs/     uvicorn/worker/local_worker logs, worker heartbeats and pid
  cache/    what can be made or downloaded again: frames/, crop.json, wiki_transcripts/, quote_sources/
  backups/  database copies and data taken out of it before risky changes
media/      source videos and PDFs, one folder per universe: avatar/{atla,korra,atla-2026,seven-havens,comics}/
library/    what videos share: music/ (the music library), frames/ (frame PNGs), sounds/ (sound effects),
            maps/ (a universe's world map, see editor/maps.py), fonts/
projects/   the editor's projects (editor_projects_root in settings.json can point elsewhere)
archive/
```

Every stored path is relative, so the whole folder moves by changing `ROOT_DIR`: files the app makes in `<data>` relative to it (`Scene.keyframe_paths`, a comic page's `Candidate.image_path`; resolve with `config.data_path`, write with `config.stored_path`); a source file relative to `media/` - `Source.file_path` is a `MediaPath` column and `Candidate`/`Background`/`Quote` derive from `store.MediaFile`, which store it relative and hand code a full path (`config.media_path` / `config.media_stored`), and cache keys hash the relative form; a photo's paths relative to its project folder (`render.on_disk` resolves a candidate).

## Commands

Run from the repo root in Git Bash:

```
./start.sh    # backend on :8000 (with embedded free worker) + Vite dev server on :5173
./stop.sh     # stops both by matching process command lines (see stop.ps1)
```

Logs: `<data>/logs/uvicorn.log`, `<data>/logs/local_worker.log`, `<data>/logs/worker.log`, `.run/frontend.log`. `start.sh` runs uvicorn without `--reload`, so backend changes need `./stop.sh && ./start.sh`. For auto-reload, run it by hand from `backend/`:

```
.venv/Scripts/python.exe -m uvicorn app.main:app --port 8000 --reload
```

Paid captioning worker (never started by `start.sh`; can also be started/stopped from the Pipeline page via `/api/worker/start|stop`):

```
cd backend && .venv/Scripts/python.exe -m app.pipeline.worker
```

**Do not start this worker unless the user asks** - it makes LLM calls for every un-captioned scene of every pending source and spends real money / subscription quota.

Frontend (from `frontend/`):

```
npm run dev
npm run build    # tsc -b && vite build - this is the type check
npm run lint     # oxlint
```

`backend/scripts/editor_cli.py` drives the video editor through the running backend (standard library only): `universes`, `list`, `create --title ... --script <file> [--notes <file>] [--show ...]`, `status <id>`, `estimate <id>`, and `voice <id>`, which places a paid voice-over order - run that one only when the user asks. The sibling `script-writer` project's `/video` skill uses it to turn a finished script into a project.

One-off scripts (from `backend/`): `scripts/ingest_episode.py <video> --book N --episode N --title "..."` runs the full pipeline on one file without the UI; `scripts/normalize_tags.py` merges casing/plural tag variants.

There are no tests, and no Python linter/formatter is configured.

## Architecture

### Pipeline and the two workers

Stages live in `backend/app/pipeline/stages/`, each a `run_*(db, source)` function that is idempotent (skips if its output already exists). `pipeline/runner.py` composes them:

- `LOCAL_STAGES` (free, GPU only): transcribe (faster-whisper; runs of 5+ identical lines - Whisper stuck on music/silence - are dropped, see `services/transcript_repeats.py`) -> detect shots (PySceneDetect) -> group shots into scenes -> extract keyframes (ffmpeg) -> build transcript chunks.
- `STAGES` = `LOCAL_STAGES` + caption (LLM) + embed.

Two separate workers poll the DB every 5s, split strictly by whether they cost money:

- **Local worker** (`pipeline/local_worker.py`) runs as a daemon thread inside the FastAPI process (started in `app/main.py`). It runs `LOCAL_STAGES` on sources with status `paused`, leaving them at `ready_for_captioning`, and drains the free reindex queues (text, visual, transcript-chunk embeddings).
- **Paid worker** (`pipeline/worker.py`) is a separate process. It runs the full `STAGES` on any source whose status is not in `TERMINAL_STATUSES` (`indexed`, `failed`, `paused`, `ready_for_captioning`), and drains the episode-summary queue.

Anything that needs an LLM call belongs on the paid worker; anything free belongs on the local worker.

The "queues" are not a separate table: they are the `Source.status` string plus boolean `*_requested` flags on `Source`. API endpoints in `api/sources.py` only flip these; workers do the work and clear them. Long reindex loops re-read their flag on every scene so a Cancel from the UI takes effect mid-run.

Note that `POST /api/sources` and `/scan-folder` create sources as `pending`, which only the paid worker picks up, and nothing in the code currently sets `paused` - so newly added sources wait for the paid worker to run all stages.

Each worker writes a heartbeat JSON to `<data>/logs/` every 10s; `api/worker.py` reports a worker as stopped when the heartbeat is older than 30s.

### Universes

A universe (`services/universes.py`) is a group of shows and films set in the same fictional world. Everything a prompt needs to know about a particular world is data on the universe - name, one-paragraph description, member shows, the word for a season, a closed list of regions, what each region's scenery looks like - so the prompts stay generic and a new world is one new entry, not rewritten prompts. Entries live in `<data>/universes.json` (created from built-in defaults on first use); a show no universe claims gets a bare universe of its own, so nothing from another world leaks into its prompts. Don't hard-code show names, nations or world knowledge into prompts - read them from the universe.

### Fan-wiki transcripts

A universe can name a fan wiki (`transcripts_wiki`, a MediaWiki API URL) whose "Transcript" namespace holds an episode transcript per page: spoken lines with speaker names, and written descriptions of what happens on screen between them. They have no timings. `services/wiki_transcripts.py` downloads them (cached in `<data>/cache/wiki_transcripts/`), finds each episode's page by rare-word overlap with our Whisper transcript (no titles needed), and aligns the two word by word with difflib: a wiki line gets the time of the Whisper words it matched, a Whisper line gets the speaker its words belong to, and a description gets the gap between the lines around it. `scripts/import_wiki_transcripts.py` applies this: fills `TranscriptLine.speaker`, removes runs of 3+ Whisper lines that share no word with the page (invented over music; runs containing lines spoken elsewhere in the show, like the opening narration, are spared), and stores every wiki line and description with its matched time range in `wiki_entries`. Speakers are passed to the caption and quote prompts.

Where the wiki has no transcripts (The Lord of the Rings), a screenplay gives the same: `Universe.screenplays` lists plain-text screenplays under `media/` (`media/lotr/screenplays/`), `services/screenplays.py` parses one by indentation (action and scene headings / speaker cue / dialogue / page furniture) into the same entries, and the same importer (`--universe lotr`) aligns it as one more page. A screenplay is a draft, not the film - scenes were cut, added (an extended edition) and reworded - so it removes no Whisper lines, needs only 40% of its words found, and a description is placed only next to a line of it that was found.

`services/wiki_descriptions.py` turns those entries into a text per scene (`Scene.wiki_description`): the descriptions whose time range overlaps the scene, plus the wiki's lines spoken in it. A scene with dialogue but no description gets no text and is not indexed - a bare line says nothing about what is on screen and crowds out described scenes. Descriptions that share one gap between two lines are spread over it in page order, in proportion to their length. `scripts/index_wiki_descriptions.py` embeds these into `scene_wiki_vec` (same text model as captions). This is a free text index covering ~70% of scenes of every episode with a wiki page, next to the paid caption index that covers only captioned episodes; both are searched by `/api/search` (text/hybrid) and by the editor's footage search, where a candidate carries `text_score`, `wiki_score` and `visual_score`. `scripts/compare_wiki_index.py` measures it against the other indexes.

`services/quote_bank.py` + `scripts/import_quote_bank.py` build the quote bank (`quote_bank` table): quotes from curated collections - the Wikiquote pages listed on the universe (`quotes_wiki`, `quote_pages`) or a plain text file - are located in the wiki transcript lines of the episode the collection files them under, which gives each a time range; exchanges longer than 45s are cut into several clips. `/api/quote-bank` filters by wording, speaker and shows; the editor's Quotes tab has a Quote bank card that adds a clip through the same endpoint as a hand-picked one. The editor's quotes stage also shows the bank (clips up to 40s) to its first Claude call: a quote picked from it by number skips the episode-reading step. Proposed quotes are kept short - a sentence or two, dropped if the cut clip is over `MAX_QUOTE_SECONDS` (12s) - so from a banked quote, which is usually a whole exchange, Claude copies only the words to play (`bank_part`) and those are located in the audio. With the project's experimental `quote_cuts` setting on (a checkbox on the Quotes tab), a proposed quote may be cut together from up to three pieces of one moment (`Quote.parts`): they play back to back with a hard cut, the renderer treating each piece as its own clip and audio splice; setting a quote's range by hand makes it one continuous clip again.

### Comics

A comic is a source like an episode, with `Source.kind = "comic"`: a PDF (`POST /api/sources` with a `.pdf` path; series title, part number and universe are read from the file name, see `services/comics.py`). One PDF is one part of a series; the series is its `show_title` and is listed under the universe's `comics`, apart from `shows` - footage search looks in the shows, and in a comic only for a shot written for that comic. Each page is a `Scene`: `start_time` is the page number from 0, its one keyframe is the page rendered to a JPEG (`<data>/comics/<source id>/`). The pipeline for a comic is `run_comic_pages` (free, local) -> caption -> embed (`runner.stages_for`); the caption uses the same schema as a scene with its own instruction, and is told the page number and what the page before was about. Pages go into the text index only - no visual index, transcript or shots. Captioning a comic is paid like any other (about 75 Claude calls per part). The scene page shows a page as the page image or the PDF itself opened at it (`ComicPageView`; `/api/media/{id}/stream` serves a PDF as `application/pdf`), with no player, transcript or shots.

The fan wiki also has transcripts of most comics, in the same form as episodes and with no page numbers. `services/wiki_comics.py` places them on pages: the PDFs are scans, so each page is read with OCR (`rapidocr-onnxruntime`, local, ~1s a page, cached in `<data>/comics/<source id>/ocr.json`), and a wiki line goes to the page its letters are found on - compared by runs of 4 letters, because OCR of comic lettering loses the spaces, and keeping the lines in page order. A description, or a line OCR missed, goes between the found lines around it. A comic's wiki pages are found by wording, so a collection of short stories gets several. `scripts/import_wiki_comics.py` stores the entries in `wiki_entries` (`start_time` = the page) and gives pages without a caption their `character_tags` - the speakers on the page (a name not among the tags in use needs 3+ pages) and the known names its descriptions mention; captioned pages keep the caption's tags. `scripts/index_wiki_descriptions.py` then writes `Scene.wiki_description` for pages too (a page with a description, or with 100+ characters of dialogue) and embeds it, so a comic with no captions is searchable and counts as indexed for the editor: shot queries offers it, and `pick_pages` reads a page's caption or, without one, its wiki text.

In the editor the shot-queries stage is told which comics are in the library, with who appears in each (from the described pages' character tags - the model may not know a recent comic), plus the project's `footage_notes` (the author's notes on where the script's material comes from, edited on the Pipeline tab), and puts a comic's title, alone, in a slot's `shows` when the narration there is about that comic; `search_slot` then searches the comic's pages by text whatever the project's search mode. Find footage then has Claude read the descriptions of all the comic's indexed pages and pick the page for every shot sent to it (`editor/comic_pages.py`, one call per comic, like the quotes stage reads whole episodes); the vector search's pages stay as alternatives, adjacent shots of a beat given the same page become one, and a shot Claude finds no page for is re-queried for the shows. A page candidate has `kind = "comic"` and `image_path`; `render._comic_args` shows it as a column in the middle of the screen (`comic_width` of the screen's width, no frame) scrolling from its top to its bottom over the slot, over the blurred background scenery or, without it, the blurred page. At `comic_width` 1 the page covers the screen: nothing is drawn behind it and the screen is a window moving down the page. The scenery track is built only where some clip leaves room for it to show (`render.needs_background`: not a full-width page, footage shown full screen, or a photo); elsewhere its pieces are cheap black filler, so it keeps its timing.

### Photos

For a shot about the real world that the shows never showed (voice actors, the creators, real people and places the story drew on), the shot-queries stage writes `Slot.photo_query`. Find footage then looks for photos on Wikimedia Commons (`services/commons.py`: the lead image of the Wikipedia article the query finds, if it is on Commons, then Commons' own file search, which is noisy) - Commons because every file there has a free licence and a named author. Up to 8 are downloaded to `<project>/photos/` and one Claude call with the Read tool (`editor/photos.py`) keeps those that really show it, best first; the result is cached per query in `photos/searches.json`. Kept photos become the slot's first candidates (`kind = "photo"`, `credit` = the attribution), ahead of the clips found for its text/visual queries. `render._photo_args` shows a wide photo filling the screen with a slow pan, any other whole over a blurred copy of itself. The Video tab lists the credits of the photos in use, for the video's description.

### Still-only shows

A show whose video must not be reused (copyright - Avatar: Seven Havens) is listed in its universe's `still_shows`. It is indexed and searched like any other, but `render` shows a slot of its footage as one frame of the clip - the scene's keyframe when one falls inside the clip, else its middle (`render.still_time`), read from the video at full resolution - with a slow pan over it, enlarged a little to make room (`STILL_MOVES`: left to right, right to left and the four diagonals; picked from a hash of the frame, never the same as the still before it). The frame is enlarged `STILL_UPSCALE` times before `zoompan` so its whole-pixel steps don't judder, and the move is drawn at the output rate (smooth at 48 fps). Such a show gives no scenery to the background stage (and scenery chosen from it earlier is skipped at render time) and is never quoted. The clip page marks its candidates STILL and, for the selected one, shows the frame that will be used (`.../candidates/{i}/still`), a strip of frames across the scene and the player: any of them can be picked (`Candidate.still_at`, set through the slot PATCH; null goes back to the keyframe). Frames are cut by `GET /api/media/{source_id}/frame?t=` and cached in `<data>/cache/frames/`.

### Captioning providers

`stages/caption.py` has three providers, chosen at call time: `claude_code` (default - shells out to headless `claude -p` with a JSON schema, billed to the Claude subscription), `api` (Anthropic SDK with a forced tool call, metered), and `local` (Ollama; uses a deliberately narrower prompt/schema because small VLMs invent character names and plot). `stages/episode_summary.py` reuses the same provider switch.

The caption schema is built per universe (`build_caption_schema`). Tags exist only for exact filtering, so there are two kinds: `character_tags`, and location as two fields - `region` (an enum of the universe's regions, stored in `Scene.region`) and `place_tags` (optional named place at city level, stored in `Scene.location_tags`). Free-form mood/action tags are no longer requested (`mood_action_tags` stays in the table for old captions). The "known names" hint sent with each call is the 20 most used characters and places of that universe; places are taken only from scenes captioned with the region prompt, because older location tags mix levels of detail.

`Scene.model_version` is written as `provider:model:caption-<hash>`, where the hash is derived from the prompt + schema - editing either changes it automatically, which is how stale-prompt scenes are found.

### Settings

`app/config.py` reads `backend/.env` (static: models, Whisper device, scene-grouping thresholds). `services/runtime_settings.py` layers `<data>/settings.json` on top for caption provider / model / API key, editable from the UI's settings modal with no restart. The modal has tabs (Models, Captioning, API keys, Usage); Models holds one default Claude model (`editor_llm_model`) and per-task overrides - captions (`caption_model`, which for the Ollama provider names the local model instead) and each editor task. Code that needs those three values must go through `current_caption_*()` / `current_anthropic_api_key()`, not `settings.*` directly.

### Storage and search

Everything is one SQLite file, `<data>/index.db` (outside the repo, with keyframes and audio under `<data>/` - see Data). ORM models are in `db/models.py`; vectors live in `sqlite-vec` virtual tables created by raw SQL in `db/session.py` and accessed through `vectorstore/sqlite_vec_client.py`:

- `scene_text_vec` FLOAT[1024] - `Scene.context_description` embedded with Qwen3-Embedding-0.6B
- `scene_visual_vec` FLOAT[1152] - first keyframe embedded with SigLIP2
- `scene_wiki_vec` FLOAT[1024] - `Scene.wiki_description` (fan-wiki account of the scene), same text model
- `transcript_chunk_vec` FLOAT[1024] - `episode_summary + chunk text`

The dimensions are hard-coded to those models; changing `text_embedding_model` / `visual_embedding_model` means recreating the vec tables and re-embedding. Some comments and docstrings still say "BGE" / "CLIP" from earlier models.

`/api/search` (`api/search.py`) is hybrid: the query is embedded with the text model and with SigLIP's text tower (text-to-image), each KNN is run over its table, and results are merged with reciprocal rank fusion. Tag/book/episode filters are resolved to candidate scene ids first and passed into the KNN. `/api/transcript-chunks` is a separate, coarser RAG-style retrieval over ~60s sliding transcript windows, independent of scene boundaries.

`Scene` and `TranscriptChunk` denormalize `show_title` / `book` / `episode_number` from `Source` for cheap filtering; `PATCH /api/sources/{id}` keeps scenes in sync.

### Schema changes

There are no migrations (alembic is in requirements but unused). `init_db()` calls `create_all`, which creates missing tables but never alters existing ones - a column added to an existing model must also be added with `_ensure_column(...)` in `init_db()` (`db/session.py`), as `scenes.region` is.

### Video editor (in progress)

`backend/app/editor/` + `api/editor.py` + the Editor tab turn a narration audio file into a video built from indexed footage. It is a separate module that only reads the index - it never writes to `index.db`. A project belongs to one universe and takes footage only from that universe's shows (all of them, or the ones picked for the project). State lives on disk: one folder per project under `<root>/projects` (or `editor_projects_root` in `<data>/settings.json`) holding `project.json`, `transcript.json` (word timings) and the audio.

Stages (`editor/stages.py`) run one at a time per project on a background thread (`editor/jobs.py`); progress is written to `project.json` and the UI polls it. The project's `visual_notes` (the author's wishes for the picture, set in the New video dialog or on the Pipeline tab; new videos take them from their preset) are read by shot queries and background. "Run to the end" (a checkbox in the New video dialog) (`POST /run-all`, `api/editor.remaining_stages`) queues every stage from the first one with missing output through the render - quotes never (they wait for approval), music only when asked (paid). Implemented so far: `transcribe` (word timestamps, script proper nouns passed to Whisper as hotwords; where Whisper got stuck repeating one phrase - with hotwords it can chant the hotword list over minutes of real narration - that stretch is transcribed again on its own without them, `_redo_stuck`; then, with a script, the words are spelled as the script has them - matched with difflib, Whisper's timings kept, a short stretch heard differently re-timed from the script, ad-libs and numbers left as heard, and a script that matches under half the words not used at all, `align_to_script`) and `beats` (one headless Claude call via `editor/llm.py`; every editor LLM call names its task (`runtime_settings.EDITOR_TASKS`) and uses `editor_llm_model(task)`: the task's override (`editor_llm_models` in `settings.json`; quotes default to Opus), else `editor_llm_model` - Sonnet unless set otherwise; both are set from the settings modal; `auto` passes no `--model`, so Claude Code uses its own default - the caption model can be `auto` too, for the CLI provider only). Beats tile the timeline with no gaps and are split into slots of at most 5s, one clip each - except a beat told wholly from a comic: when Find footage has Claude read the comic (`comic_pages.pick_pages`), it also decides how many pages the beat shows and on which word of the narration each comes on, and the beat's slots are rebuilt to those times (at least `MIN_PAGE_SECONDS` a page, no upper limit). `queries` (one Claude call per 40 beats) writes two queries per slot - a narrative one for the caption index and a no-names frame description for the visual index; `select` (`editor/footage.py`, free) searches both, scores hits as z-scores against a random sample of each index so the two are comparable, and assigns clips in narration order without reusing a scene. Where a clip is cut from the episode is shot-aware (`_clip_window`): the window must contain the moment the scene was found by, and among the positions that do - centred, or starting/ending on a nearby cut - the one with no sliver of a shot (< 0.8s, which reads as a flicker) wins. Candidates carry their flicker count and lose score for it, and a clip that would still end just off a cut trades up to 1s with the next clip in the beat (`end_on_a_cut`), so slots within a beat are not always equal; each run starts again from the even split unless the beat has a locked clip. Shots are of two kinds. Most only illustrate and are searched as above. A shot where the narration tells of one particular event of the story (when in doubt the prompt asks for a moment) gets `Slot.moment` and the 1-3 episodes the shot-queries call expects it in (`moment_episodes`, from an episode list in its prompt); Find footage handles these first (`editor/moments.py`): a headless Claude session per few moments gets Bash restricted to `editor/finder_tool.py` (`search` through the running backend's `/api/search` with show/season/episode filters, `episode <id> [--from --to]` to read an episode scene by scene with dialogue, `scene <id>`) and finds each moment its own way, answering with the scene and the time (M:SS); the clip is cut around that time, the scenes are reserved before any illustrative shot is searched, a moment it doesn't find goes to a second session told not to trust the guessed episodes, and one not found then either is left to the ordinary search. The answers are cached per moment in `<project>/moments.json` - "not found" only when both sessions said so (`looked_twice`); a shot a session gave no answer for is asked again on the next run. A slot whose search finds nothing (typically a shot sent to a comic with no indexed pages - shot queries only offers comics that have some, and names the rest as unavailable) gets new queries for the shows from one Claude call for all such slots (`_requery`) and is searched again; if that still finds nothing it is searched by its beat's narration over everything. Each slot keeps 8 candidates; a slot the user picks or re-searches is locked and survives re-runs - unless the stage is run with `unlock` (the UI asks when there are locked clips), which drops the locks when the stage starts (`Project.unlock_before`). Candidates store file path + times, not just scene ids, because re-indexing recreates scenes. The timeline is a list of segments, not the audio file's clock, because quote clips with their own audio will be inserted later. 

`render` (`editor/render.py`) outputs 1920x1080 H.264 at 24000/1001 fps. With the project's `frame_rate` set to 48 it outputs 48000/1001 instead, without changing the plan: slot lengths, audio cuts and the background track stay counted in 24 fps frames, footage is composed at 24 and each frame repeated (in exact pairs), and only comic pages and photo pans are drawn at 48 - so they move smoothly. Each slot is encoded to its own file in `<project>/segments/`, named by a hash of everything that affects its pixels, then the segments are concatenated without re-encoding and the narration is muxed in - so a re-render only encodes what changed (bump `ENCODE_VERSION` after changing the filter graph). Segment lengths are computed from absolute frame positions so rounding never drifts against the audio. Most of a clip's time goes to filters, not to x264, so the graphs do nothing twice: a still layer (comic page, photo, frame artwork, corner mask) is read, scaled and converted once and then repeated (`STILL`, never `-loop 1`, which decodes and filters the picture again for every frame), and the background is blurred and dimmed at its small size before it is enlarged. Two layouts: `simple` (clip fills the screen) and `framed` (clip in a window over a blurred, darkened background, with a frame PNG from `<root>/library/frames/` overlaid on top; the window is detected from the PNG's transparent opening). Some source files are 4:3 inside a 16:9 file with baked-in black bars - `source_crop()` detects this once per file (cached in `<data>/cache/crop.json`). 

`background` (`editor/background.py`) picks one calm scenery shot per beat for the framed layout: one Claude call writes a no-names scenery description per beat, then a visual search runs only over scenes whose indexed keyframe looks like empty scenery (top 6% by a zero-shot scenery-vs-characters score computed from the vectors already in the index; near-black keyframes are skipped). Only the single shot around that keyframe is used, and each beat gets several shots (enough to cover its length with spare). At render time `editor/bgtrack.py` lays them end to end at normal speed with ~0.8s cross-fades into one continuous 480x270 track on the video clock (quotes included), built from small cached pieces - the part of each shot that plays alone and each cross-fade - then concatenated; clips seek into that track and blur/dim it when compositing. Without chosen scenery the background falls back to a blurred copy of the foreground clip. With the `background` feature off (see Features) the stage is skipped by run-all and refused, and render ignores scenery chosen earlier.

`quotes` (`editor/quotes.py`) proposes lines of dialogue to drop into the narration, with no vector search: Claude reads the narration and the list of episodes and says what line it wants, after which sentence, and in which 1-3 episodes it expects to find it; Claude then reads the full transcripts of those episodes (a few per call - an episode is only ~3k tokens) and picks exact `TranscriptLine` ids, or nothing; the fragment is re-transcribed with word timestamps to find the exact cut, since the index only has line-level timings. Reading whole episodes beats retrieving one-minute chunks: the model sees who is talking and matches meaning rather than wording. It relies on the model knowing the show; for worlds it doesn't know, episode summaries would have to be added to the first step. A last Claude call (`_review`) then hears every cut clip in its place - the narration before it, the words actually cut, the narration after - and keeps it, moves it to a sentence boundary nearby, or drops it: a clip that splits two sentences that lean on each other, repeats the narrator, or is a fragment of a speech goes. There is no limit on how many quotes a video gets; the model judges, and none is a fine answer. Quotes are proposals until the user approves them. An approved quote plays with its own audio between two beats and lengthens the video; beat and slot times stay on the narration clock, and the renderer splices quote segments and audio in at beat boundaries (cut on the same frame for video and audio). Once beats exist, a quote's position snaps to the nearest beat boundary; the beats stage splits beats at quote positions. Any episode with a transcript can be quoted.

`voiceover` (`editor/voiceover.py`, the Voice tab) voices the project's script through the Lumean API (`services/lumean.py`, ElevenLabs voices; key `lumean_api_key` in `settings.json`, set from the settings modal) instead of uploading narration audio. Lumean takes a voice only through a template, so each project keeps one Lumean template in step with its voice settings; an order cuts the script into fragments, and each fragment is kept with its text and audio (`<project>/voiceover.json`, `<project>/voiceover/`) so it can be voiced again alone with other wording - a retry of a failed or policy-rejected fragment is free, regenerating a finished one is paid. The stage only brings local state in line with the order (send the script if there is no order, wait, download what changed), so re-running it is free; it can place a paid order, so it is started only from the Voice tab's endpoints, not `/run/voiceover`. The joined audio becomes the narration on request (or by itself when the project has none), which resets the transcript, beats and quotes like an upload does. A new project starts with its preset's voice, and the script can be made ready for the voice first (`editor/voice_text.py`, `POST /api/editor/voice-text`, the "Optimize for voice" button under a script field): one Claude call adds directions like `[whispers]` where the delivery changes, pauses, and spells out numbers, by ElevenLabs' guidance for v4/v3; the words must stay, and the places where they came back different are reported (`changed_words`). Where the script is read for anything but voicing (Whisper hotwords, the beats prompt) the directions are stripped (`voice_text.spoken`). Written from Lumean's API reference and exercised only against a local fake of it - not yet against the live service. The API lives at `api.lumean.net` (the reference says `.app`, which does not answer); the key is `lumean_api_key` in settings, else the `LUMEAN_KEY` environment variable.

`music` (`editor/music.py`, the Music tab) puts music under the narration, also through Lumean. One Claude call divides the beats into blocks of one mood (at least 35s, whole beats) and writes a generator prompt for each, describing the universe's own sound without names (`Universe.music_style` can spell that sound out). A generated track is at most 30s, so a block is filled with several different tracks from the same prompt - up to 4 per order, a few orders at a time - and no track is played twice. Generated tracks fade out towards their end, so each is measured (`usable_range`: only the part before the fade is played) and the next comes in over its last 3s (`OVERLAP`); every track is brought to the same loudness, `music_level` LU below the narration's. Every composed track is also filed in the music library (`editor/music_library.py`): `<root>/library/music` (or `music_library` in `settings.json`) holding every track as `<hash of the audio>.<ext>` in one folder and `library.json` with each track's prompt, mood, the universe it was composed for, measurements and the projects it plays in. Before ordering, a block takes library tracks of any universe whose prompt is almost its own (a prompt names its world's instruments, so another world's track is only as close as its sound) (`REUSE_SIMILARITY`, cosine of the text embeddings - different moods of one video already reach ~0.95) so the library does not fill with more of the same; with the project's `music_library_only` (a checkbox on the Music tab) nothing is ordered and blocks are filled with the closest tracks there are. When Lumean fails (an error, an order with nothing back, out of time), the blocks it could not fill take the closest library tracks the same way, and the stage fails only if those are not enough. A track in the library is played from there - the project keeps its measurements and `library_id`, not a copy of the audio (`music_library.file_of`; `MusicTrack.from_library` marks one taken rather than composed for this video); it plays once per video, the least used first; one the user unticks is marked rejected and not offered again, and "compose this block again" does not take back what the block had (`MusicBlock.avoid`). `scripts/import_music_library.py` files the tracks of existing projects. Blocks and tracks are in `Project.music`, files of tracks not in the library and the built mix in `<project>/music/`; blocks planned for beats that have since changed are ignored until the stage runs again. The mix is built at render time (`build_track`, cached by its recipe) on the narration's clock and mixed into the narration pieces only (`render._soundtrack`), fading out before a quote and back in after it - a quote keeps the show's own sound.

Standard sound effects (`editor/sounds.py`, a card on the Music tab): a page turn for comic pages and a camera shutter for photos, each generated once through Lumean (`sfx` orders, 3 variants, silence trimmed off the start and brought to one peak) into `<root>/library/sounds/`, shared by every project. At render time `build_narration` mixes them into the narration at the start of every slot showing that kind (`sfx_volume` dB below the peak; `sound_effects` turns them off), before quotes and music are spliced in.

Presets (`editor/presets.py`, `<data>/presets.json`, the Presets tab of the settings modal) are what a new video starts with, by name - a channel, a series, a language: universe (empty = chosen per video) and shows, features, look, voice, visual wishes, footage prompt, the "Optimize for voice" instructions and "run to the end". The New video dialog fills its fields from the chosen preset; the project copies them and remembers the preset (`Project.preset`), so editing a preset leaves existing videos alone. "Save to preset" on a project's Voice and Look tabs and its Features writes back to its preset. The project's preset is shown at the top of its page (`ProjectPresetBar`); clicking it opens the settings on Presets, which, opened on a video's page, show that video's preset - picking another there applies it (`POST /apply-preset`): it becomes the project's preset and its features, look and voice are copied into the project; universe, shows, script and notes stay, as footage already found depends on them. Opened anywhere else, the list only picks which preset to edit. A `default` preset always exists (made on first use from the single defaults `settings.json` held before).

Features (`presets.Features`: background, music, sound_effects, quotes, photos, comics, maps, voiceover) are what a video uses besides footage. A preset holds them, a new project copies them into `Project.features`, and the project's Pipeline tab can change them (Features, folded) or save them back to the preset. A feature turned off is hidden from the project page - its tab, stage row, Look section, card or button - and the backend honours it too: its stages are refused (`api/editor._require`, and again in the stage function for one queued earlier), run-all skips them, shot queries asks for no photos and offers no comics (`store.project_comics` is empty), and render leaves out scenery, music, sound effects and approved quotes. Projects and presets saved before features get them from the switches their look held then (`music_enabled`, `sound_effects`, `background_scenery`, `presets.features_from_look`).

Map shots (`editor/maps.py`, the "Map…" button of a slot on the Clips tab): a journey drawn on the map of the universe's world, for narration about where someone went. A universe names its map (`Universe.map`, a folder of `<root>/library/maps/`: `map.json` - the picture, font and credit; `places.json` - every place with its pixel position, side (`good`/`evil`) and an optional picture in `places/`; `routes.json` - journeys as point lists; plus the two medallion frames and the leader, generated once with GPT Image in the style of the map's cartouche). A shot (`store.MapShot`, on a `Candidate` of `kind = "map"` with no file) goes from one place to another, along a journey (`_span` cuts it between the two places, walked forwards - a journey can pass a place twice) or straight. The map lies on a table seen at `tilt` degrees (a shot's own, or by default the project's `map_tilt` from the Look tab - `maps.with_look` fills it in wherever a shot is drawn); the camera starts close on the first place, draws back over the whole way while a dashed line is drawn along it, and closes in on the last. Lines, rings and names lie in the map's plane and are laid on as ink (multiplied into the paper); a place with a picture gets a medallion standing up, pinned with the leader, in the frame of its side. The frames are drawn with OpenCV and piped to ffmpeg with the segments' encode settings, so `render` caches and joins them like any segment (a job may be a callable instead of ffmpeg arguments); `maps.identity` makes the cache key, including the files' times. A place's picture is made on request with GPT Image (`generate_picture`, paid, the OpenAI key from settings), a piece of the map around the place being the style reference.

`test-data/` (git-ignored) holds a sample narration, script and frame image for developing this.

### Frontend

`src/api/client.ts` is the single API layer: hand-written TypeScript types mirroring the Pydantic schemas in `backend/app/schemas/scenes.py`, with the backend URL hard-coded to `http://localhost:8000` (no Vite proxy). Changing a response schema means updating both. Pages use TanStack Query; routes are declared in `src/App.tsx`.
